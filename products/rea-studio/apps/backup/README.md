# REA Backup — working development version

This application performs actual local snapshots, deduplication, integrity checks and restores in two explicitly separate formats. Existing `.rea-backup` application snapshots remain unchanged. A new native mode creates, opens, extends and restores bounded local **restic repository versions 1 and 2** using independently implemented encryption, keys, packs, indexes and trees. It is **not a complete replacement for restic 0.19.1** and has no established full-product superiority.

## Run and verify

From `products/rea-studio`, run `npm start`, open the printed local address and select **Lab Backup**. Run application checks with:

```text
node --test apps/backup/app.test.mjs apps/backup/app.integration.test.mjs apps/backup/native.test.mjs
```

Create a fixture through the new-file form or put regular files in the Backup application's dedicated workspace. Snapshot a relative source folder, refresh the snapshot list, select a snapshot and verify it. Restore requires explicit confirmation and always creates a new destination folder. Retention first previews the exact recovery points and chunks to remove; its apply action requires confirmation and an unchanged plan token.

## Existing application snapshots

- SHA-256-addressed 1 MiB fixed-size file chunks stored once per unique content; whole-file SHA-256 identity; immutable, SHA-256-addressed JSON snapshot manifests with labels, source, dates and file/directory records. Empty files have no chunks.
- Regular binary files, nested and empty directories, file lengths and modification timestamps. Source files are checked for size, timestamp and inode changes while reading; detected changes abort manifest creation. This does not supply an atomic filesystem snapshot.
- Existing chunks are checked before reuse. Full integrity checks validate every stored chunk and reconstructed file hash/length, as well as the manifest's own hash and safe paths.
- Restore validates the complete snapshot and preflights all file modification times before creating output. On the tested Windows Node runtime, times outside 1970-01-01 through 2106-02-07T06:28:15.999Z are refused because `utimes` wraps them. File times use JavaScript's represented millisecond precision and are read back within one millisecond before success. Invalid JavaScript dates are rejected as malformed manifests. Restore refuses existing destinations and verifies chunks again while writing. Runtime failures can leave a partial new restore folder, clearly reported; existing destination files are never overwritten.
- Keep the newest N snapshots, retain all chunks they reference and remove unreferenced chunks only after an explicit preview/confirmation. Every retained snapshot's data is verified before a retention plan is allowed: a damaged newest snapshot cannot cause deletion of an older intact recovery point.
- Serialized local operations; persistent data survives host restarts. Limits: 10,000 entries, 64 MiB per file, 512 MiB total source data per snapshot. The application repository is `.rea-backup/{chunks,snapshots}` inside the dedicated Backup workspace.

Tests exercise greater-than-2-MiB binary restoration, duplicate content, empty paths, manifest/chunk corruption, overwrite/traversal refusal and confirmed retention against actual disk storage. Authenticated custom manifests cover invalid/unrepresentable times before output, preserved existing destinations, and real timestamp read-back at epoch, 2038 and the Windows upper boundary. HTTP tests cover the live application host and persistence across restart.

## Native restic repositories

The **Encrypted restic repositories** form offers create/open, snapshot listing, capture, inspection, verification and restore. Its repository, source and destination paths stay inside the Backup workspace. Enter a password for each operation; the field clears afterward, and neither the password nor decrypted master keys are saved in app records or returned by the API. The encrypted native key file is necessarily saved in the repository. New repository creation refuses every existing destination, including an empty folder. Native restore includes the snapshot's top-level source directory; application snapshot restore copies that directory's contents instead.

The HTTP actions are `nativeInit`, `nativeInfo`, `nativeList`, `nativeSnapshot`, `nativeInspect`, `nativeCheck` and `nativeRestore`. Every request supplies `repository` and `password`; initialization additionally accepts `version` (1, default, or 2), capture accepts `source` and optional `label`, inspection/check accepts a full snapshot `id`, and restore adds `destination` and `confirm: true`. Native actions never interpret an application snapshot as a restic snapshot.

- Native scrypt key files derive 64 bytes; authenticated master keys and config use AES-256-CTR with Poly1305-AES. Random salts, nonces, repository IDs and degree-53 irreducible chunker polynomials are independently generated. This code uses Node cryptographic primitives plus a new BigInt Poly1305 implementation; it does not execute restic.
- Native v1 and v2 writes use valid uncompressed blobs and JSON metadata. V2 reads additionally decode original zstandard metadata and compressed data/tree pack records, with expansion limits. Data and tree packs remain separate. Object storage IDs and plaintext blob IDs are verified against SHA-256, and index offsets/lengths/types are checked against authenticated pack headers.
- Capture writes immutable packs, then their index, then the referencing snapshot. Completed object bytes are synchronized and atomically linked from a temporary file. This is not a power-loss durability guarantee for directory entries. Existing referenced data is verified before reuse. Native snapshot `paths` uses a logical `/<source-directory-name>` path, and its tree contains that directory and its descendants; original absolute-path construction is not reproduced.
- Reads obtain a snapshot before loading its indexes. Snapshot inspection validates bounded regular-file/directory trees, Unicode names, ordering, duplicate/case collisions and relative paths. Verification checks all referenced file data and lengths. This is a **selected-snapshot check**, not a whole-repository repair, orphan-pack check or full equivalent of `restic check --read-data`.
- Snapshot time and optional node `mtime`/`atime`/`ctime` use bounded Go-compatible timestamp parsing: real Gregorian dates, year 0000–9999, no leap seconds, uppercase `T`/`Z`, and at most 128 characters. The original's comma fractions, single-digit hours and offset `+24:00`/`+00:60` forms are accepted; JSON `null` denotes Go's year-0001 zero time. Numeric/coerced dates, impossible calendar days, hour 24, space separators and lowercase forms are rejected consistently by listing and selected-snapshot reads. Fractional input can exceed nine digits, but native conversion and list ordering have millisecond precision; listing sorts actual instants rather than timestamp text.
- Restore verifies the selected snapshot before creating output, refuses existing destinations, rereads authenticated data while writing, and restores file/directory modification times with JavaScript millisecond precision. Original nanosecond precision is not reproduced. Failures after output creation leave an explicitly reported partial new folder. No existing destination is overwritten.
- On the tested Windows Node runtime, `utimes` silently wraps seconds outside 1970-01-01 through 2106-02-07T06:28:15.999Z. Native restore rejects modification times outside that interval **before output creation**, even when the timestamp and repository are valid for restic, and checks the applied modification time within one millisecond. Null/zero-time or year-0000/9999 file times therefore remain inspectable/verifiable but cannot be restored here. Snapshot time alone does not constrain restore, and access/change times are validated but not restored.
- Every native operation uses an authenticated **exclusive** restic lock, with the original's 200 ms second conflict check. Existing locks, including stale ones, cause refusal and are never removed automatically. Normal exits remove only the app's own lock; crashes can leave it behind. Locks are not periodically refreshed. Native operations have a two-minute cooperative deadline and do not support cancellation.

Bounds: 64 MiB per restored/source file, 512 MiB per snapshot, 96 MiB per pack, 16 MiB per metadata/tree document, 64 MiB cumulative stored and decoded metadata/tree bytes per operation, 10,000 tree entries/snapshots, 4,096 indexed packs, 100,000 index records, 100 directory levels, 1,024 content IDs per file, 16 keys and 4 GiB cumulative pack reads per operation. Cached pack bytes are limited to the most recently loaded pack. Scrypt accepts power-of-two N from 2 to 262,144, r 1–32, p 1–64, N×r ≤ 1,048,576 and N×r×p ≤ 8,388,608, with a 144 MiB allocation guard. Repositories outside these bounds are explicitly rejected, even if valid for restic. These are application guards, not operating-system memory/CPU isolation.

The native suite authenticates the preserved official release ZIP and executable, copies the original CLI to each test's private temporary directory, then uses only synthetic repositories and passwords. Tests independently exercise original-generated v1/v2 backups (including confirmed original compression), app-generated v1/v2 repositories, original `check --read-data` and restores, app appends/restores, malicious but authenticated trees, MAC/storage/plaintext failures, malformed pack/index records, excessive KDF/expansion, locks, overwrite protections, backward custom-format behavior and HTTP restart persistence. Authenticated timestamp fixtures compare malformed trees/snapshots and valid Go parser boundaries with the original, including nanosecond/long/comma fractions, offsets, year limits, null, and native/original restore within the supported Windows interval. The original can panic on malformed tree timestamps; tests record nonzero exit, without claiming graceful original rejection. See [native validation](native-validation.json) and [source comparison](SOURCE-COMPARISON.md) for the exact observed boundary.

## Concrete parity gaps and limitations

Application-format backups remain **unencrypted** and cannot be opened by restic. Native mode is interoperable within the tested local-format boundary, but writes fixed 1 MiB chunks, one blob per pack, and no compression. It does not reproduce Rabin chunk boundaries, pack randomization/batching or compression policy. The revised [password derivation policy](KDF-POLICY.md) measures a synthetic probe and writes N=32,768/r=8/p=13–32, retaining the highest p observed in three original runs on this machine. It differs from original calibration and does not rewrite existing p=1 keys. The [prior validation](native-validation.json) retains its historical source identities; the [policy follow-up](results/kdf-policy-validation.json) records current focused checks. BigInt MAC arithmetic is not claimed constant-time, and no cryptographic security audit has been performed. Do not infer production security equivalence from interoperability tests.

Native key addition/removal/password changes, remote/object-store backends, mount APIs, complete command-line compatibility, include/exclude policies, scheduling, repository repair, forget/prune policy families, per-host/source/tag retention, parallelism and resource throttling remain absent. Native retention is not implemented; the existing retention buttons affect only `.rea-backup` snapshots.

Ownership, ACLs, extended attributes, symlinks, hard-link identity, devices, sparse-file structure and filesystem snapshots are not preserved by this slice. Native capture records portable mode bits, but restore does not apply modes. Metadata outside the supported name/type/content/mtime fields is not reproduced. Unsafe Windows names and arbitrary non-Unicode Unix names are rejected. Source mutation checks can miss adversarial or same-timestamp changes. Native source changes or aborted captures can leave immutable unreferenced packs without publishing a snapshot; native repair/cleanup is not implemented. Custom aborted chunks may remain until its confirmed retention cleanup. The trusted local filesystem must not be concurrently replaced with malicious symlinks; checks do not eliminate adversarial path replacement races.

No measurement demonstrates lower CPU/memory use, higher reliability, or faster execution than restic. SHA-256 matching and chunk reuse support implemented integrity/deduplication behavior only.

Official native contracts are pinned to restic v0.19.1 commit `6aa3a516ce654808a1f28f9fa21e9b7c8e6e90bf`: [repository format](https://github.com/restic/restic/blob/6aa3a516ce654808a1f28f9fa21e9b7c8e6e90bf/doc/design.rst), [backup](https://github.com/restic/restic/blob/6aa3a516ce654808a1f28f9fa21e9b7c8e6e90bf/doc/040_backup.rst) and [restore](https://github.com/restic/restic/blob/6aa3a516ce654808a1f28f9fa21e9b7c8e6e90bf/doc/050_restore.rst). The complete documented product remains broader than this slice.

The implementation uses newly written Node.js code and standard-library file/crypto/zstandard APIs; no restic or prior reconstruction code is imported. The original CLI is used only by independent tests.
