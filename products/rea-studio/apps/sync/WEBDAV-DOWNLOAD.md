# Reviewed WebDAV to local copy — source draft

This is a separately authored slice for generic rclone `vendor=other` WebDAV, against parent `beab1f3668cf652e7663f3fd7216ac607506ac06`. It has not been imported, syntax checked, built, tested or executed locally. Independent source review and exact-source hosted finite/original/browser validation remain pending. Historical upload and local results are unchanged and do not accept this direction. Full rclone, provider, platform, security, performance and all-ten replacement completion remain false.

The **Copy from WebDAV** card previews a remote collection into a nonempty relative local workspace directory. Selected files are copied or replaced under explicit approval. Destination-only files stay in place; empty source folders are not created. Binary bytes and observed remote modification times are retained on successful copies. Anonymous or request-scoped Basic authentication uses fresh credentials for each request. Password fields clear on success and rejection; a click rejected by the UI's busy guard preserves the in-flight form inputs. Username edits invalidate the displayed plan. Every UI rejection or request failure drops the displayed token and approval, requiring a new preview; the busy guard is the sole exception. A failed same-direction service preview can leave its older private plan valid, but the UI no longer displays that token.

## API and selection

`createDAVDownload(workspace, {clock}?)` provides `preview`, `apply`, `cache`, `close`:

- `preview({endpoint, auth?, source:'remote/subfolder', destination:'local/target', mode:'copy', filters?, comparison?})`. An empty remote source means the endpoint collection. The remote source must exist; the local target may be missing. No file or directory is created in preview.
- `apply({endpoint, auth?, token})`. The host action additionally requires the exact boolean `confirm:true`. Source and destination cannot be overridden at apply. Endpoint and anonymous/Basic username principal must match the private plan. Passwords are not cached or persisted; a changed server password can be supplied under the same principal.
- Host actions are `webdav-download-plan` and `webdav-download-apply` under the existing `webdav-*` dispatcher. No Sync/shared host routing edit is needed. `webdav-status` adds `downloadCache`, while the sanitized last-result record uses `direction:'webdav-to-local'`.

The seven boolean comparison options remain `checksum`, `sizeOnly`, `ignoreSize`, `ignoreTimes`, `ignoreExisting`, `update`, `noUpdateModtime`. They use the existing generic `compareDAV` decision function with the remote file as source and local file as destination. Generic WebDAV has no shared hashes or supported comparison-time precision: equal size may skip different bytes, and checksum requests fall back to size. Safety SHA256 values are separately shown through `byteHashesEqual`; they do not change original selection rules. Update compares destination time minus source time with the pinned original one-second fallback. Local submillisecond boundary equivalence is not established by this draft.

The existing bounded filter subset is accepted. Unknown keys, sync/deletion, vendor selection, empty-directory creation flags, time-window overrides and unsupported filter/comparison options are refused instead of ignored. Every source file requires a valid modification date and strong ETag, including filtered/skipped files. These are stricter native safety conditions and are not original failure parity.

Preview returns an opaque token, direction, bound endpoint/source/destination, operations, skipped reasons, resolved options, expiration and `{copy,replace,mkdir}` counts. Operations are `mkdir` or `copy`; a missing target root uses `mkdir` with path `''`. An existing-file copy contains its reviewed destination metadata. Apply returns `{applied,direction,completed,retainedAt,transaction}`; verified file records contain type/path/size/SHA256. No operation deletes an extra local file or sends remote PUT, DELETE or MKCOL.

## Guards, staging and partial failure

Both complete inventories, including excluded entries, are fingerprinted again before local work. Remote GETs carry If-Match and are checked against preview lengths/hashes again while staging. Portable relative path rules, canonical root identity, case/NFC collisions, reserved names, directory/file collisions, links, single-link regular files and bounded stable reads apply locally. Existing directory components are resolved without creating them in preview.

Apply consumes the token before its first possible write, including a recovery directory or staging file. All selected bytes are written exclusively into a new guarded `.rea-sync-history/dav-download-<token>/` directory and read back before target publication. Replacement preimages are separately written and verified, with numbered files and a path/hash manifest. This history is local, unencrypted and retained without automatic pruning. Sufficient free space is required for staged bytes and preimages. It is a recovery record, not automatic rollback or crash-resume.

Missing directories are created only after approval. New files are published through an exclusive hard link from the verified same-volume stage, then the stage link is removed. Existing files are rechecked immediately before a per-file rename. Completed files are read back, assigned observed source timestamps and checked again. Manifest progress uses staged local writes and rename; no durable power-loss journal is claimed. The tree is not atomic. An external process can race between checks and rename; the destination must be quiescent. There is no cross-process lock or filesystem compare-and-swap primitive in this slice.

Failures after token consumption include verified completions, recovery location and whether the current target may already have changed. HTTP errors start with the partial-state disclosure before the shared host's 600-character truncation. A timestamp/readback error after rename may leave new bytes installed even when that file is not counted as verified. A pre-publication staging error leaves target bytes unchanged but may leave diagnostic staging files. Status persistence failure explicitly says completed local work occurred. Reuse of consumed/expired tokens is refused; restart discards volatile plans and retains status/history.

Upload and download actions share one immediate busy guard. Starting a preview in the opposite direction closes that direction's cached plans; displayed tokens there need a new preview. This keeps serialized metadata within the existing workspace cap instead of doubling it. A download service retains one plan, at most8MiB serialized metadata, for15minutes. Combined inventory is10,000 entries, depth32,64MiB per file and512MiB guarded aggregate file-read work; repeated staging/readback consumes that byte budget too. Client request/response/header/aggregate bounds stay unchanged. The120second operation guard is checked between work items; one in-flight request can add its30second deadline, and filesystem operations are not preemptible. Actual JS overhead/transient buffers exceed serialized metadata size.
