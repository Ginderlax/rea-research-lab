# REA Backup — working development version

This application performs actual local snapshots, deduplication, integrity checks and restores in two explicitly separate formats. Existing `.rea-backup` application snapshots remain unchanged. A new native mode creates, opens, extends and restores bounded local **restic repository versions 1 and 2** using independently implemented encryption, keys, packs, indexes and trees. It is **not a complete replacement for restic 0.19.1** and has no established full-product superiority.

## Run and verify

From `products/rea-studio`, run `npm start`, open the printed local address and select **Lab Backup**. Run application checks with:

```text
node --test --test-concurrency=1 apps/backup/app.test.mjs apps/backup/app.integration.test.mjs apps/backup/native.test.mjs apps/backup/restic-compression.test.mjs apps/backup/restic-compression-review.test.mjs apps/backup/rabin.test.mjs apps/backup/capture-rabin-file.test.mjs apps/backup/rabin-original.test.mjs apps/backup/restic-rabin-snapshot.test.mjs apps/backup/restic-rabin-lifecycle.test.mjs apps/backup/restic-rabin-deadline.test.mjs apps/backup/restic-data-pack.test.mjs apps/backup/restic-data-pack-ownership.test.mjs apps/backup/native-host-pack.test.mjs apps/backup/native-small-mutation.test.mjs
```

Create a fixture through the new-file form or put regular files in the Backup application's dedicated workspace. Snapshot a relative source folder, refresh the snapshot list, select a snapshot and verify it. Restore requires explicit confirmation and always creates a new destination folder. Retention first previews the exact recovery points and chunks to remove; its apply action requires confirmation and an unchanged plan token.

## Existing application snapshots

- SHA-256-addressed 1 MiB fixed-size file chunks stored once per unique content; whole-file SHA-256 identity; immutable, SHA-256-addressed JSON snapshot manifests with labels, source, dates and file/directory records. Empty files have no chunks.
- Regular binary files, nested and empty directories, file lengths and modification timestamps. Source files are checked for size, timestamp and inode changes while reading; detected changes abort manifest creation. This does not supply an atomic filesystem snapshot.
- Existing chunks are checked before reuse. Full integrity checks validate every stored chunk and reconstructed file hash/length, as well as the manifest's own hash and safe paths.
- Restore validates the complete snapshot and preflights all file modification times before creating output. On the tested Windows Node runtime, times outside 1970-01-01 through 2106-02-07T06:28:15.999Z are refused because `utimes` wraps them. File times use JavaScript's represented millisecond precision and are read back within one millisecond before success. Invalid JavaScript dates are rejected as malformed manifests. Restore refuses existing destinations and verifies chunks again while writing. Runtime failures can leave a partial new restore folder, clearly reported; existing destination files are never overwritten.
- Keep the newest N snapshots, retain all chunks they reference and remove unreferenced chunks only after an explicit preview/confirmation. Every retained snapshot's data is verified before a retention plan is allowed: a damaged newest snapshot cannot cause deletion of an older intact recovery point.
- Serialized local operations; persistent data survives host restarts. Limits: 10,000 entries, 64 MiB per file, 512 MiB total source data per snapshot. The application repository is `.rea-backup/{chunks,snapshots}` inside the dedicated Backup workspace.

Tests exercise greater-than-2-MiB binary restoration, duplicate content, empty paths, manifest/chunk corruption, overwrite/traversal refusal and confirmed retention against actual disk storage. Authenticated custom manifests cover invalid/unrepresentable times before output, preserved existing destinations, and real timestamp read-back at epoch, 2038 and the Windows upper boundary. HTTP tests cover the live application host and persistence across restart.

## Native restic repositories

The **Encrypted restic repositories** form offers create/open, snapshot listing, capture, inspection, verification and restore. The source-authored key-management candidate adds key listing, addition, removal and password replacement. Its repository, source and destination paths stay inside the Backup workspace. Enter a password for each operation; all three password fields clear after a completed or rejected native attempt, and neither passwords nor decrypted master keys are saved in app records or returned by the API. A busy guard rejects an overlapping attempt without clearing inputs belonging to the active request. The encrypted native key file is necessarily saved in the repository. New repository creation refuses every existing destination, including an empty folder. Native restore includes the snapshot's top-level source directory; application snapshot restore copies that directory's contents instead.

The HTTP actions are `nativeInit`, `nativeInfo`, `nativeList`, `nativeSnapshot`, `nativeInspect`, `nativeCheck`, `nativeRestore`, `nativeKeyList`, `nativeKeyAdd`, `nativeKeyRemove` and `nativeKeyPasswd`. Every request supplies `repository` and `password`; initialization additionally accepts `version` (1, default, or 2), capture accepts `source`, optional `label` and `compression` (`auto`, default, `off`, `fastest`, `better`, or `max`), inspection/check accepts a full snapshot `id`, and restore adds `destination` and `confirm: true`. Native actions never interpret an application snapshot as a restic snapshot.

Key addition and password replacement take `newPassword` and matching `newPasswordConfirm`, plus optional `username` and `hostname` (blank uses best-effort operating-system metadata). Password replacement additionally requires `confirm: true`. Both derive a fresh wrapping key with a new salt, save it, read the saved key back, verify the unchanged repository master key and authenticate the same config bytes before success. Addition preserves every existing key. Password replacement then removes only the key used to authenticate that request; it preserves other credentials and all existing backup payloads. If old-key removal fails after new-key verification, the error names both IDs and explains that both credentials may remain usable. Sixteen existing keys prevent either operation because verified replacement needs a temporary extra key.

`nativeKeyRemove` requires `keyID` (a full lowercase hexadecimal ID or unique prefix) and `confirm: true`. It refuses the currently authenticated key. Mutation inventories treat unused key contents as bounded opaque bytes, require unchanged names and exact bytes, and keep the existing lock, confinement, regular-file, size and time guards; unrelated malformed metadata or damaged storage hashes do not prevent explicit removal. The authenticated access key and each newly verified key still require SHA-256, password/MAC and config validation. `nativeKeyList` returns `currentKeyID`, display `keys` and `keyWarnings: [{ id, message }]` for storage-hash, JSON or display-metadata failures; it does not hide file/directory, size, read-stability or deadline failures. Absent/null user and host names display as empty strings, and absent/null creation times display Go's year-0001 zero time. Warning rows can select another key for confirmed removal. Readable malformed entries never expose salts or wrapped key data in this display.

Credential scanning can bypass per-key storage-hash, UTF-8/JSON, base64 or wrapped-data defects and try a later key. This repair-friendly behavior is an explicit bounded policy: pinned restic 0.19.1 `SearchKey` skips authentication failures but can stop on other key-load errors. The candidate still stops for directory/count/name errors, unsafe links or nonregular/oversized files, unstable reads, excessive or unsupported scrypt parameters, deadlines and authenticated config/layout failures. This is not a claim of complete command-line error equivalence.

An empty access password requires the boolean `insecureNoPassword: true` on every request, including initialization; its omitted default is false. An empty newly added/replacement password separately requires boolean `newInsecureNoPassword: true`; its omitted default is also false. The corresponding fields must be exactly empty when either flag is true; a supplied nonempty password is never silently discarded. Both new fields must match. Empty-password keys provide no password barrier to anyone who can read the repository. The UI presents separate insecure options for access and new-key creation.

Removal success returns `removedKeyID`, `currentKeyID`, `remainingKeys`, `configUnchanged: true`, `keyRemoved: true` and `postRemovalVerified: true`. If deletion completed but a subsequent inventory/config/deadline check fails, the error begins `Restic key <ID> was removed. Post-removal verification did not complete`; inspect remaining keys before retrying. Direct calls also receive `removedKeyID`, `currentKeyID`, `keyRemoved: true` and `postRemovalVerified: false` on the error. The existing HTTP error envelope carries the frontloaded disclosure in its message, subject to its 600-character limit. It does not claim rollback of a completed deletion.

These key-management changes and their focused regression sources have not been executed or syntax-checked locally. Hosted Windows 2022 / Node 24.16.0 execution, pinned original `key list/add/remove/passwd` comparisons, real-browser verification and security assessment remain pending. Historical native validation below does not validate this candidate or close `RESTIC.ENCRYPTION.001`.

- Native scrypt key files derive 64 bytes; authenticated master keys and config use AES-256-CTR with Poly1305-AES. Random salts, nonces, repository IDs and degree-53 irreducible chunker polynomials are independently generated. This code uses Node cryptographic primitives plus a new BigInt Poly1305 implementation; it does not execute restic.
- Native v1 writes remain uncompressed. V2 writes compress new data/tree blobs and metadata using Node/libzstd with a 512 KiB window and disabled frame checksum. `off` disables compression for file data; nonempty trees and v2 metadata still compress, following the original format contract. Existing blobs are authenticated and reused across mode changes. V2 reads decode original zstandard metadata and compressed data/tree pack records, with expansion limits. Data and tree packs remain separate. Object storage IDs and plaintext blob IDs are verified against SHA-256, and index offsets/lengths/types are checked against authenticated pack headers. See [compression implementation and evidence](COMPRESSION.md).
- Native capture uses source-assisted Rabin content-defined chunks with the repository polynomial, a 64-byte window, 512 KiB minimum and 8 MiB maximum. It collects distinct encrypted data blobs into sequential data-only packs with a 16 MiB target; tree packs stay separate. Pending and indexed data identities deduplicate. It writes immutable packs, then their index, then the referencing snapshot. Completed object bytes are synchronized and atomically linked from a temporary file. Deadline/cancellation guards precede sink calls and final success; pre-commit deadline checks follow awaited write steps. Committed results retain explicit warnings when own temporary-file or lock cleanup fails. This is not a power-loss durability guarantee for directory entries. Existing referenced data is verified before reuse. Native snapshot `paths` uses a logical `/<source-directory-name>` path, and its tree contains that directory and its descendants; original absolute-path construction is not reproduced. See [Rabin implementation and lifecycle evidence](RABIN.md) and [data pack aggregation and operation ownership](PACKS.md).
- Reads obtain a snapshot before loading its indexes. Snapshot inspection validates bounded regular-file/directory trees, Unicode names, ordering, duplicate/case collisions and relative paths. Verification checks all referenced file data and lengths. This is a **selected-snapshot check**, not a whole-repository repair, orphan-pack check or full equivalent of `restic check --read-data`.
- Snapshot time and optional node `mtime`/`atime`/`ctime` use bounded Go-compatible timestamp parsing: real Gregorian dates, year 0000–9999, no leap seconds, uppercase `T`/`Z`, and at most 128 characters. The original's comma fractions, single-digit hours and offset `+24:00`/`+00:60` forms are accepted; JSON `null` denotes Go's year-0001 zero time. Numeric/coerced dates, impossible calendar days, hour 24, space separators and lowercase forms are rejected consistently by listing and selected-snapshot reads. Fractional input can exceed nine digits, but native conversion and list ordering have millisecond precision; listing sorts actual instants rather than timestamp text.
- Restore verifies the selected snapshot before creating output, refuses existing destinations, rereads authenticated data while writing, and restores file/directory modification times with JavaScript millisecond precision. Original nanosecond precision is not reproduced. Failures after output creation leave an explicitly reported partial new folder. No existing destination is overwritten.
- On the tested Windows Node runtime, `utimes` silently wraps seconds outside 1970-01-01 through 2106-02-07T06:28:15.999Z. Native restore rejects modification times outside that interval **before output creation**, even when the timestamp and repository are valid for restic, and checks the applied modification time within one millisecond. Null/zero-time or year-0000/9999 file times therefore remain inspectable/verifiable but cannot be restored here. Snapshot time alone does not constrain restore, and access/change times are validated but not restored.
- Every native operation uses an authenticated **exclusive** restic lock, with the original's 200 ms second conflict check. Existing locks, including stale ones, cause refusal and are never removed automatically. Normal exits remove only the app's own lock; crashes can leave it behind. Locks are not periodically refreshed. Native operations have a two-minute cooperative deadline and do not support cancellation.

Bounds: 64 MiB per restored/source file, 512 MiB per snapshot, 96 MiB per pack, 16 MiB per metadata/tree document, 64 MiB cumulative stored and decoded metadata/tree bytes per operation, 10,000 tree entries/snapshots, 4,096 indexed packs, 100,000 index records, 100 directory levels, 1,024 content IDs per file, 16 keys and 4 GiB cumulative pack reads per operation. Cached pack bytes are limited to the most recently loaded pack. Scrypt accepts power-of-two N from 2 to 262,144, r 1–32, p 1–64, N×r ≤ 1,048,576 and N×r×p ≤ 8,388,608, with a 144 MiB allocation guard. Repositories outside these bounds are explicitly rejected, even if valid for restic. These are application guards, not operating-system memory/CPU isolation.

The native suite authenticates the preserved official release ZIP and executable, copies the original CLI to each test's private temporary directory, then uses only synthetic repositories and passwords. Tests independently exercise original-generated v1/v2 backups (including confirmed original compression), app-generated v1/v2 repositories, original `check --read-data` and restores, app appends/restores, malicious but authenticated trees, MAC/storage/plaintext failures, malformed pack/index records, excessive KDF/expansion, locks, overwrite protections, backward custom-format behavior and HTTP restart persistence. Authenticated timestamp fixtures compare malformed trees/snapshots and valid Go parser boundaries with the original, including nanosecond/long/comma fractions, offsets, year limits, null, and native/original restore within the supported Windows interval. The original can panic on malformed tree timestamps; tests record nonzero exit, without claiming graceful original rejection. See [native validation](native-validation.json) and [source comparison](SOURCE-COMPARISON.md) for the exact observed boundary.

## Concrete parity gaps and limitations

Application-format backups remain **unencrypted** and cannot be opened by restic. Native mode is interoperable within the tested local-format boundary and now reproduces the bounded Rabin boundary contract. Its sequential data pack aggregation does not reproduce original concurrent or randomized batching, custom chunker APIs, original encoder bytes or original compression levels. The revised [password derivation policy](KDF-POLICY.md) measures a synthetic probe and writes N=32,768/r=8/p=13–32, retaining the highest p observed in three original runs on this machine. It differs from original calibration and does not rewrite existing p=1 keys. The [prior validation](native-validation.json), [policy follow-up](results/kdf-policy-validation.json) and [compression follow-up](results/compression-validation.json) retain their exact historical source identities. BigInt MAC arithmetic is not claimed constant-time, and no cryptographic security audit has been performed. Do not infer production security equivalence from interoperability tests.

Native key-management acceptance remains pending for the source-authored candidate above. Remote/object-store backends, mount APIs, complete command-line compatibility, include/exclude policies, scheduling, repository repair, forget/prune policy families, per-host/source/tag retention, parallelism and resource throttling remain absent. Native retention is not implemented; the existing retention buttons affect only `.rea-backup` snapshots.

Ownership, ACLs, extended attributes, symlinks, hard-link identity, devices, sparse-file structure and filesystem snapshots are not preserved by this slice. Native capture records portable mode bits, but restore does not apply modes. Metadata outside the supported name/type/content/mtime fields is not reproduced. Unsafe Windows names and arbitrary non-Unicode Unix names are rejected. Source mutation checks can miss adversarial or same-timestamp changes. Native source changes or aborted captures can leave immutable unreferenced packs without publishing a snapshot; native repair/cleanup is not implemented. Custom aborted chunks may remain until its confirmed retention cleanup. The trusted local filesystem must not be concurrently replaced with malicious symlinks; checks do not eliminate adversarial path replacement races.

No measurement demonstrates lower CPU/memory use, higher reliability, or faster execution than restic. SHA-256 matching and chunk reuse support implemented integrity/deduplication behavior only.

Official native contracts are pinned to restic v0.19.1 commit `6aa3a516ce654808a1f28f9fa21e9b7c8e6e90bf`: [repository format](https://github.com/restic/restic/blob/6aa3a516ce654808a1f28f9fa21e9b7c8e6e90bf/doc/design.rst), [backup](https://github.com/restic/restic/blob/6aa3a516ce654808a1f28f9fa21e9b7c8e6e90bf/doc/040_backup.rst) and [restore](https://github.com/restic/restic/blob/6aa3a516ce654808a1f28f9fa21e9b7c8e6e90bf/doc/050_restore.rst). The complete documented product remains broader than this slice.

The application uses Node.js file/crypto/zstandard APIs and its own repository implementation. Rabin rolling arithmetic is a source-assisted translation of the pinned upstream contracts, with original source and BSD attribution preserved. The original CLI is used only by independent tests.
