# Classic WinZip AES-256 ZIP subset

This source adds a bounded classic WinZip AES ZIP implementation to REA Archive. It is source-authored and awaits exact-source hosted tests and independent qualification. It does not establish full 7-Zip or WinZip compatibility, security certification, performance improvement, or universal superiority. Existing 7Z AES and its historical receipts describe a separate format and source epoch.

## Product behavior and request contract

Create a ZIP using `format: "zip"`, `encryption: "aes256"`, a request-scoped `password`, and `compression: "store"` or `"deflate"`. Creation writes AE-2, encrypting regular-file payloads individually. Directory entries stay unencrypted; an archive containing only directories reports `encrypted: false`. File names, paths, sizes, dates, ZIP comments and archive structure remain visible. ZIP header encryption is unsupported. A password supplied without the explicit method is refused with `Choose AES-256 ZIP encryption before supplying a ZIP password.` The refusal still precedes file collection and output writes.

The module API is `makeZip(entries, compression = 'deflate', options = {})`, with `options.encryption = 'aes256'`, `options.password` and an optional shared `OperationBudget`. Reading uses `readZip(buffer, includeData = false, { password, operationBudget } = {})`; existing two-argument calls remain valid. HTTP create, list, test and extract use their existing actions. Every list/test reads and validates all data; even a listing with visible names needs the correct password when encrypted files exist. Extraction requires confirmation and a new destination. The server decodes and validates the entire archive before creating that destination or staging its members.

AE-1 and AE-2 AES-256 ZIP inputs are read. Successful encrypted entries report `encrypted: true`, `encryption: "winzip-aes256"`, `aesVersion`, `authenticationVerified: true`, and `contentChecksum`. AE-1 retains and verifies the recorded CRC-32. AE-2 requires a zero wire CRC and reports `contentChecksum: false`; its entry result omits `crc32` rather than representing zero as a recorded content checksum. The authentication trailer is still mandatory. `headerEncrypted` is false for ZIP.

Writer passwords contain 1–99 ASCII code units, U+0020 through U+007F inclusive. An explicit reader password may contain 0–99 of those units; omitted and intentionally empty passwords are distinct. NUL, control characters below U+0020, CR/LF and non-ASCII input are refused. This is a deliberate, testable profile of the pinned Windows program's actual source: the writer accepts its simple-ASCII range, while its reader's UTF-8 conversion branch is disabled and active password conversion uses the system ANSI code page. Arbitrary UTF-8 passwords are not claimed. U+007F acceptance follows the source range; real console behavior remains a hosted oracle probe. Unicode file names and contents are supported independently of this password restriction.

## Wire contract and ordering

The reader requires encrypted bit 0, method 99 and matching local/central AES extras (ID `0x9901`). Extras contain version 1 or 2, vendor `AE`, strength 3 and underlying stored (0) or DEFLATE (8) compression. At least seven AES-extra bytes are required; identical trailing extension bytes are accepted in both headers. Extraction version 5.1 is required for this scoped profile. Unknown versions, vendors, strengths, methods and inconsistent downgrade metadata are refused.

A file payload contains a 16-byte random salt, two-byte password verifier, encrypted compressed bytes and ten-byte HMAC-SHA1 tag. PBKDF2-HMAC-SHA1 uses 1,000 iterations; its first 66 derived bytes provide 32-byte AES key, 32-byte authentication key and two-byte verifier. The original rounds its internal derived allocation up to 68 bytes, while consuming this identical 66-byte prefix. The AES counter starts at zero, preincrements its little-endian low 64 bits for the first block, and retains zero in its upper 64 bits. The implementation uses native AES-256 ECB only to encode counter blocks, then XORs their output with compressed payload bytes; file plaintext is not encrypted as ECB blocks. A default big-endian AES-CTR counter would produce incompatible bytes. HMAC covers ciphertext, not salt, names or other ZIP metadata. Both the password verifier and authentication trailer must match before decrypting a payload.

Reading has three phases: validate every central/local header, size, path and nonoverlapping data range; authenticate/decrypt every AES compressed payload; then inflate or copy any member and verify decoded sizes and applicable CRCs. A bad later authentication tag therefore prevents inflation of earlier members, including plain members in mixed archives. No partially validated entries are returned. This ordering and the API's refusal before destination writes are new tests, not a claim that unauthenticated ZIP metadata becomes cryptographically protected.

## Bounds, memory and secret lifetime

The existing limits remain 10,000 entries, 16 MiB decoded per file, 64 MiB decoded in total and 68 MiB input ZIP. Packed encrypted sizes include the 28-byte salt/verifier/tag overhead. A shared cooperative operation budget covers collection, format traversal, KDF accounting, CRC work, authentication, per-counter batches and verification. Defaults remain 15 seconds and two billion work units; explicit limits remain bounded by 60 seconds and eight billion units. Budget checks occur before/after native KDF/HMAC/compression and between bounded counter batches. Native calls, memory copies, filesystem waits and garbage collection cannot be interrupted by these checks; this is not worker/process isolation or a wall-clock guarantee.

The reader retains all authenticated compressed plaintext until the authentication phase is complete. Their aggregate is bounded by validated nonoverlapping slices of the 68 MiB input. Decoding can additionally retain up to 64 MiB of returned plaintext plus native codec/internal copies. Creation also holds original input, compressed data, encrypted output and container assembly copies. No fixed RSS or single-copy claim is made. Owned password-byte copies, derived keys, counter blocks, keystream batches, tags and temporary decrypted compressed buffers are overwritten on their covered paths. Failed decoded output buffers are overwritten before errors propagate; successful returned file data remains available to its caller. JavaScript strings, caller input, native crypto internal state and garbage collector copies cannot be promised erased. Request passwords are not intentionally written to workspace records; queued handlers retain their captured password only for the request. Hosted HTTP/browser tests must verify their recorded persistence/cleanup observations.

## Explicit exclusions

This slice excludes ZipCrypto, PKWARE strong encryption, AES-128/192, newer WinZip GCM formats, encrypted ZIP64, encrypted data descriptors, encrypted method-93 Zstandard, encrypted directory entries, metadata/name encryption, split/multidisk/SFX archives, unsupported vendor/extra versions, archive updating and large streaming/parallel operations. Unencrypted ZIP/ZIP64, data descriptors, method-93 Zstandard, timestamps and path checks remain part of the existing regression scope. The application's limits are much smaller than the complete original product's capabilities.

The new core tests include a separately authored wire-envelope constructor using standard crypto primitives, per-block counter construction and independent bitwise CRC. These are specification cross-checks, not original-CLI provenance, independently frozen known-answer vectors, or a proof of cryptographic correctness. A separate hosted original role must authenticate the complete released `7z.exe` and `7z.dll`, retain sanitized command transcripts and exact synthetic archive/file bytes, and check candidate-to-original and original-to-candidate stored/DEFLATE archives. Independently constructed AE-1 fixtures must first pass the complete original's test/extraction before native comparison. The complete program is the oracle; `7zr.exe` is an acquisition bootstrap only and cannot serve as a ZIP oracle.

New core, HTTP and DOM modules and five additional genuine browser scenarios are separately identified. Tests, builds, crypto, original programs and browser runs occur only in supported verified cloud runners. Public results must bind actual commit, parent, closure, before/after source and the correct original-product/component boundary.
