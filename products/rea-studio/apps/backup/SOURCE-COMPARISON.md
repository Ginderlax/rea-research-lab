# Native restic format comparison

This is a source-assisted new implementation of a bounded native repository slice, not independent binary recovery or full restic replacement. The production app never calls an original executable, vendor runtime, prior reconstruction, shell command or remote backend.

Baseline: [restic v0.19.1 release](https://github.com/restic/restic/releases/tag/v0.19.1), commit `6aa3a516ce654808a1f28f9fa21e9b7c8e6e90bf`. The repository design and relevant crypto/key/pack/tree/lock source contracts were read; broader user documentation was consulted for the scope boundary:

- [Repository design](https://github.com/restic/restic/blob/6aa3a516ce654808a1f28f9fa21e9b7c8e6e90bf/doc/design.rst): layout, storage/plaintext IDs, encryption/key derivation, v1/v2 metadata, compression, pack/footer records, index supersession, trees, snapshots, lock conflict checks and read/write publication ordering.
- [Crypto](https://github.com/restic/restic/blob/6aa3a516ce654808a1f28f9fa21e9b7c8e6e90bf/internal/crypto/crypto.go) and [KDF](https://github.com/restic/restic/blob/6aa3a516ce654808a1f28f9fa21e9b7c8e6e90bf/internal/crypto/kdf.go): AES-256-CTR, AES-128(nonce) additive Poly1305 pad, ciphertext MAC, salt length, key byte division, nonzero nonce validation and master-key JSON.
- [Repository keys](https://github.com/restic/restic/blob/6aa3a516ce654808a1f28f9fa21e9b7c8e6e90bf/internal/repository/key.go), [config](https://github.com/restic/restic/blob/6aa3a516ce654808a1f28f9fa21e9b7c8e6e90bf/internal/restic/config.go), [pack parser/writer](https://github.com/restic/restic/blob/6aa3a516ce654808a1f28f9fa21e9b7c8e6e90bf/internal/repository/pack/pack.go) and [lock](https://github.com/restic/restic/blob/6aa3a516ce654808a1f28f9fa21e9b7c8e6e90bf/internal/restic/lock.go).
- [Node](https://github.com/restic/restic/blob/6aa3a516ce654808a1f28f9fa21e9b7c8e6e90bf/internal/data/node.go) and [tree](https://github.com/restic/restic/blob/6aa3a516ce654808a1f28f9fa21e9b7c8e6e90bf/internal/data/tree.go): additional Go quoting layer for names, portable metadata, UTF-8 byte ordering, tree serialization newline and child content/subtree references.
- [Snapshot](https://github.com/restic/restic/blob/6aa3a516ce654808a1f28f9fa21e9b7c8e6e90bf/internal/data/snapshot.go), and the preserved executable's reported Go 1.26.4 [time JSON contract](https://github.com/golang/go/blob/a9ce111d580581fb925ae88f125c69b7d93504ea/src/time/time.go) and [RFC3339 parser](https://github.com/golang/go/blob/a9ce111d580581fb925ae88f125c69b7d93504ea/src/time/format_rfc3339.go): Gregorian calendar validation, null zero-time behavior, fractional seconds, and the original's permissive comma/hour/zone fallback. These additional pinned references were read after independent timestamp review; no Go runtime or source module is imported.
- [Encryption/key management](https://github.com/restic/restic/blob/6aa3a516ce654808a1f28f9fa21e9b7c8e6e90bf/doc/070_encryption.rst), [initialization](https://github.com/restic/restic/blob/6aa3a516ce654808a1f28f9fa21e9b7c8e6e90bf/doc/030_preparing_a_new_repo.rst), [backup](https://github.com/restic/restic/blob/6aa3a516ce654808a1f28f9fa21e9b7c8e6e90bf/doc/040_backup.rst) and [restore](https://github.com/restic/restic/blob/6aa3a516ce654808a1f28f9fa21e9b7c8e6e90bf/doc/050_restore.rst) clarify the broader behavior left incomplete.

Exact bytes and SHA-256 of these references are recorded in `native-source-references.json`. Existing preserved design/reference manifests were inspected; `projects/09-restic/reconstruction.mjs` and its runtime/output code were not read or used. Attribution: restic is BSD-2-Clause; its existing [upstream license](../../../../projects/09-restic/UPSTREAM-LICENSE.txt) is retained.

The official Windows amd64 ZIP's publisher digest was independently reread from the GitHub release API before the final oracle run. ZIP SHA-256: `da948ad707ed690426473aaba2046cd61f8f90f6f0e7dab6be0d5796531de67d`. Preserved extracted executable SHA-256: `b0dd1fd21eea5d8fe1325f55f7118213c21f36de8a261e04c0624a5ab9fd7830`. Each oracle fixture authenticates both inputs, copies executable bytes to its own temporary directory, authenticates that private copy, and checks `restic 0.19.1` before further execution. No concurrent oracle source directory is mutated or trusted without hashing. All repository contents/passwords are synthetic; no user repository or credential is exercised.

The tests establish a format-level round trip across original and new implementations, including original `check --read-data` and original restore of our snapshots. They do not establish identical chunk IDs, tree JSON identity, CPU/memory improvements, security equivalence, complete CLI/backends/metadata or universal format acceptance. The new writer deliberately uses fixed 1 MiB chunks, one blob per pack, uncompressed v1/v2 data and metadata, fixed scrypt N=32,768/r=8/p=1, logical source paths and an exclusive lock for every action. Original restic uses Rabin chunking, batching/randomized pack assignment, v2 compression, hardware-calibrated KDF, native absolute source metadata, ordinary shared locks where possible and refresh/stale-lock workflows. BigInt MAC arithmetic has no constant-time guarantee. The README records all bounds and further missing contracts.

Independent review found that permissive JavaScript date parsing accepted numeric and impossible calendar timestamps, while selected-snapshot reads omitted snapshot-time validation. The native reader now validates all snapshot times and optional node mtime/atime/ctime fields with a newly written bounded Go-compatible parser. Tests use fully authenticated tree/pack/index/snapshot fixtures rather than unauthenticated corrupted bytes. The original accepts year 0000/9999, null, long/comma fractions, single-digit hours and `+24:00`/`+00:60` offsets; those supported forms are retained. Impossible calendar days, numeric time, hour 24, leap seconds, space/lowercase separators fail both readers, although original malformed-tree handling can terminate with a panic. The comparison does not describe that outcome as graceful rejection.

Own synthetic filesystem probes also found Windows Node 24.16.0 `utimes` wrapping modification times outside unsigned 32-bit Unix seconds. Native Windows restore now refuses mtime outside 1970 through 2106-02-07T06:28:15.999Z before creating output and verifies applied mtime within one millisecond. Valid restic times outside that interval remain readable/checkable; native restore does not claim them or nanosecond precision. The format parser accepts at most 128 timestamp characters, and timestamp ordering uses millisecond instants. Missing optional node times are not restored; access/change times are validated but not applied.

The same Windows restore-time preflight and read-back correction also applies to the separately implemented custom `.rea-backup` restore branch. Its SHA-256-authenticated manifests reject invalid JavaScript dates; valid but unsupported Windows modification times stay data-checkable and are refused before output. Separate custom tests cover that change. The native module and original comparison tests remain unchanged by the custom correction; the historical full-suite result and subsequent custom-source validation are fingerprinted separately in `native-validation.json`.

Observed corrections during development are recorded in `native-validation.json`; failed phases are not counted as successful comparison cases. The custom `.rea-backup` format remains plaintext and separate.
