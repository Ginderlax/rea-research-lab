# Bounded 7Z AES-256 candidate

This bounded slice adds genuine `7zAES` (`06F10701`) encryption and decryption to the existing bounded 7Z container. It uses its own source-assisted JavaScript KDF/folder adapter and Node's builtin AES-256-CBC primitive. The application imports no original executable, DLL, source module or third-party cipher package. The immutable staged evidence and future separately collected current installation proof bind their own source epochs. Neither establishes full7-Zip compatibility or an improvement claim. This document describes the 7Z format only. The separate [classic WinZip AES-256 ZIP subset](ZIP-AES-COMPATIBILITY.md) adds content encryption with visible names/metadata; its exact-source hosted validation is pending.

Data-bearing folders can contain AES alone (stored bytes) or AES followed by one Copy, DEFLATE, LZMA or LZMA2 decoder. Bind indexes determine decoder order; serialized coder order is not assumed. The writer encrypts after compression. Solid/non-solid data and plaintext, supported compressed or encrypted headers are supported; encrypting names is a separate option. Empty files/directories have no encrypted data stream, so a password alone does not conceal their names. Creation reports actual encrypted streams or header encryption.

Passwords become exact UTF-16LE code units for the KDF. The ordinary branch hashes salt, password bytes and little-endian UINT64 counter for `2^cyclesPower` rounds. Decoder properties accept zero/one-byte defaults, salts/IVs of 0–16 bytes, cycles powers0–20 and the released direct-key branch63. Source26.04 permits ordinary powers through24; this implementation deliberately refuses21–24 before KDF work. Direct63 is a compatibility decoding branch, not the application writer profile. The writer requires1–128 UTF16 units, uses power19, a fresh16-byte archive salt and an independent random16-byte IV for each encrypted stream. Original26.04's default writer uses no salt; the new salt choice is independently checked for format interoperability, not claimed to match its defaults. Empty passwords may be explicitly supplied when reading, but creation refuses them.

CBC blocks are zero-padded to16 bytes; the declared coder output size clips padding as the released filter does. The decoder requires exactly the matching ciphertext length. It requires a recorded unpacked folder CRC or every unpacked substream CRC for encrypted folders, which is a local restriction beyond the original format. It checks all recorded packed/folder/file and mandatory header CRCs. Missing or incorrect passwords, malformed properties/bindings, truncation, excess output and selected corruption fail before filesystem extraction. **AES-CBC and CRC are not authenticated encryption.** A controlled IV change plus rewritten CRC is explicitly demonstrated as accepted changed plaintext; these checks do not provide tamper authenticity or an adversarial integrity guarantee.

The previous16 MiB/file,64 MiB total/solid output,96 MiB archive,16 MiB header,10,000 entries/streams and128 path-component bounds remain. AES intermediate coder bytes are bounded by96 MiB; final data/header outputs retain their existing smaller bounds. Passwords are at most128 UTF16 units. A private operation context keeps at most16 derived keys, then wipes evicted/closed key and password-byte buffers. The shared cooperative budget includes KDF hashed bytes, AES bytes, codecs, metadata and CRCs; defaults remain15 seconds/2 billion units, optional API maxima60 seconds/8 billion. KDF checks occur at most64 rounds apart and between bounded operations. Native crypto calls, memory copies, filesystem waits and garbage collection are not interrupted or isolated by these checks.

These are data limits, not a fixed peak-memory limit. In addition to caller buffers, normalized file copies and solid buffers, encryption can retain compressed plaintext, a16-byte-aligned plaintext buffer, native cipher output, a concatenated ciphertext copy and the final archive. Decryption retains the archive, native decipher output, a clipped decrypted packed copy, decompressed output and copied file substreams; encoded headers add further buffers. Individual AES intermediate representations can approach96 MiB and final/solid file representations64 MiB. Temporary copies and garbage collection can overlap. Private byte buffers are wiped where owned; JavaScript password strings and native crypto internals cannot be promised erased. There is no worker/process memory isolation, streaming, or hard blocked-I/O deadline.

The 7Z creation controls offer encryption and a separate names/header checkbox. A distinct ZIP AES selector/password supports content encryption only; ZIP names and metadata stay visible, as described in [ZIP-AES-COMPATIBILITY.md](ZIP-AES-COMPATIBILITY.md). Inspection/extraction use an explicit password checkbox, allowing an intentionally empty read password. Password fields are not stored in workspace records, filenames, URLs or API results and clear after each operation and on view disposal. Pending actions disable duplicate controls; disposed views suppress late success/error publication. This is a finite local lifecycle policy, not a comprehensive credential/security audit. API request bodies necessarily carry the supplied password to the local host. Every list/test operation fully verifies contents, so a plaintext-header encrypted archive still needs its password here; original7-Zip can list that metadata without a password. There is no matching passwordless metadata-list API.

The selected released source and complete LGPL2.1-or-later notice are preserved through the exact inert [AES source/proof map](results/aes-followup/publication-index.json) and [SEVENZIP-AES-LGPL.txt](SEVENZIP-AES-LGPL.txt). The AES helper and AES-related container additions are LGPL2.1-or-later source-assisted work based on Igor Pavlov's26.04 `7zAes.cpp/.h`, filter and folder reader/writer contracts. Existing LZMA primitives retain their separate public-domain/MIT notices. The original CLI is used only in verification, authenticated by exact EXE/DLL SHA-256 before/after every new oracle call. New oracle passwords use private UTF8 stdin with the released `-sccUTF-8` conversion; values are never command arguments or retained records.
